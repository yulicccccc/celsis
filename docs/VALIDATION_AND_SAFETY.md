# Validation and Safety

## Current claim

Allowed wording:

> Prototype — Local/synthetic verification may pass; not validated for GxP use.

Do not claim:

- production validated,
- 100% safe,
- GxP ready,
- automatic approval.

## Golden validation

A Golden Case should contain:

```text
tests/golden/case_xxx/
  source.pdf or source.wkl
  source.sha256
  redaction_manifest.json
  expected.json
  reviewer_signoff.md
```

`expected.json` must be independently human-confirmed.

It must not be generated by the parser under test.

## Three-way comparison

Preferred exact comparison:

```text
Human Expected
      ==
JS / Web Engine
      ==
Python Reviewer
```

Integer RLU fields should be exact matches.

## Source classes

Recommended:

- `ORIGINAL_PDF`
- `NATIVE_WKL_EXPORT`
- `DERIVED_TEXT`
- `MANUAL_PASTE`

Derived/manual text should carry a more cautious source status and should not silently become an automatic “MATCH”.

## Hashes

A hash proves identity of the exact file copy being hashed.

It does **not** prove that the file was never altered before ingestion.

## Reviewer independence

Entry Assistant:

```text
source → expected entry values → prefill
```

Reviewer:

```text
source → independently derived expected
saved LIMS → actual
expected vs actual → discrepancy
```

Reviewer must not simply consume Entry's final output.

## Production browser safety

A future read-only Reviewer scraper should explicitly control:

- write HTTP methods,
- form submit,
- popups,
- downloads,
- service workers,
- output whitelist,
- sensitive DOM/log leakage.

Do not connect such a scraper to production before validation and authorization.

## Repository safety

Use synthetic examples in source control.

Do not commit live batch reports, credentials, sessions, or source files.
